### 2026-09-20 — the silent-commit trap

### 2026-09-24 — plan/0008 profile: the full-offload token is GPU-bound; the 28 ms host cost was a tracing artifact

The layered profile landed (perf dwarf call-graphs, 20 gdb samples, nsys with `--cuda-graph-trace=node`): full-offload decode at 28.25 tok/s is about 95 percent GPU-kernel-busy across the two sequential devices. Kernel budget per token: about 29 ms of PTQ1_0 `mul_mat_vec_q` (127 instances at 165-183 us) plus about 6.4 ms of roughly 1,700 tiny kernels averaging 3.7 us (about 1,840 kernel launches per token). The host thread's 94.93 percent of cycles under `cudaStreamSynchronize` is the driver's spin-wait, not host work. plan/0007's 1.6 ms GPU against 28 ms host split was an nsys artifact: without node-level graph tracing the replay's kernels are absent from the kernel table. Treat plan/0007's host-cost conclusions as corrected by this; its occupancy analysis stands. Graph reuse engages (99 graph captures against 24,267 launches in the traced window), which retires the can_reuse candidate. LTO is a null (28.26 vs 28.25), as the attribution predicts. Mixed ngl 37 telemetry: about 175 scheduler splits per compute (deepest about 451), oscillating CPU and CUDA inside every block, the CPU leg's disease; the mixed split itself improved to 3.30 tok/s on Arch from 2.08 under WSL2, while full offload slowed to 28.25 from 33.11 (same silicon, OS changed). Findings about the harness: this fork's llama-cli conversation mode runs on an embedded server context (tools/cli/cli-server.h), so its logs carry server lines and the decode thread is found under `server_queue::start_loop`; gdb attach needs sudo (ptrace_scope 1); llama-bench filters the `graphs reused` perf print. An operator decision is owed: close plan/0008 on the attribution branch and re-cut the GPU-leg work (matmul kernel efficiency, overlapping the two sequential devices, dispatch-floor node folding) as a new milestone, or re-scope plan/0008 itself.

### 2026-09-24 — operator rule: read the help surface before any operational run

Operator instruction: use `--help` to operationalise runs. Before invoking a tool in a run that matters, read its help surface and let that text drive the command: top-level `host-lifecycle --help` carries the verb map (a subcommand-level `--help` is not accepted; a rejected flag prints the subcommand's expected flag set, and that enumeration is the usage text for verbs like `tasks` that have no expanded help line), and the GNU tools and the fork's binaries carry their own `--help`. No guessed syntax and no trial-and-error flag probing; when a flag is rejected, the usage line in the rejection is the source of truth for the next invocation. The misses that prompted the rule, all this session: `host-lifecycle validate --help` and `tasks --help` were guesses against a binary that takes `--help` only at top level, and `llama-cli --no-cnv` was a guess against a fork whose baseline predates that flag. The invocations that worked (`--single-turn`, `--ignore-eos`, `--evidence`) each came from reading help or rejection text first.
